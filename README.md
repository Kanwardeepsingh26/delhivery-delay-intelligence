# Delhivery Last-Mile Delay Intelligence Pipeline

Capstone project, AI & ML Certification Program (E&ICT Academy, IIT Roorkee).
One connected pipeline that answers three questions for regional operations: **how long will a parcel take**, **which parcels will miss their promise**, and **which hubs need which playbook**. The data is synthetic (produced by `generate_data.py`); Delhivery's real records are never used.

Pinned feature list (17 columns) and cleaning/feature functions live in `src/shipment_prep.py` and are shared by every Part and by the scoring script.

## How to run

Run from the repository root, in exactly this order, on a fresh clone:

```bash
pip install -r requirements.txt      # pandas, numpy, scikit-learn, joblib (exact versions pinned)
             # prints: 24 1224 48
python part_a_clean_eda.py           # data/modelling_table.csv + outputs/part_a_*.csv
python part_b_regression.py          # outputs/part_b_*.csv
python part_c_classification.py      # outputs/part_c_*.csv
python part_d_segments.py            # hub profile, K-Means segments, tier mismatch
python package_model.py              # models/*.pkl + helper CSVs + outputs/part_d_reload_check.csv
python predict_delay.py              # outputs/new_shipment_actions.csv
```

`models/delay_model.pkl` is regenerated by running `python package_model.py`. A pickled scikit-learn model loads reliably only on the scikit-learn version that wrote it (pinned in `requirements.txt`: 1.9.1), so if your installed versions differ, re-run `package_model.py` instead of loading the committed pickle. Running `predict_delay.py` twice gives byte-identical output.

## Data findings

All numbers below are copied from files in `outputs/`.

1. **Express parcels are delayed most often.** From `part_a_delay_by_group.csv`: Express 0.4897 (119 of 243), Standard 0.2056 (132 of 642), Economy 0.0857 (27 of 315). Overall delay rate is 0.2317 (278 of 1,200 parcels, `part_a_checks.csv`).
2. **Delay rate rises sharply with hub tier:** Tier 1 = 0.0400, Tier 2 = 0.2150, Tier 3 = 0.4400.
3. **Delay rate rises steeply with distance:** 0-200 km = 0.0219, 201-400 km = 0.1368, 401-600 km = 0.4364, 601+ km = 0.8523 (75 of 88 parcels).
4. **Columns most correlated with `delivery_hours`** (ranked by absolute value, `part_a_correlations.csv`): `promised_hours` +0.8372, `distance_km` +0.4013, `n_stops` +0.3247.
5. **Why `declared_value_inr` was log-transformed:** on the median-filled column the mean is 1,533.05 Rupees against a median of 1,121.50 Rupees (a long right tail), while after the log transform the mean (7.0277) and median (7.0224) almost coincide, so the feature is close to symmetric and no longer dominated by a few expensive parcels.

Cleaning evidence (`part_a_checks.csv`): 24 duplicates removed (1,224 to 1,200 rows), 5 weight sentinels (999 kg) treated as missing, service-type spellings reduced from 12 to 3, and 0 nulls remain in the 17 features, `delivery_hours` and `is_delayed`.

## Model results (regression)

Files: `part_b_metrics.csv`, `part_b_tree_depth.csv`, `part_b_gb_learning_rate.csv`, `part_b_cv.csv`. Split is 840 / 180 / 180; the scaler was fitted on training rows only (training scaled mean 0.0, test scaled max column mean 0.2187, proving no leakage).

- **Baseline:** predicting the training mean gives validation R² = -0.0212 (RMSE 18.8552 hours). That means the mean explains none of the variation; any useful model has to beat zero R² clearly.
- **Winner on validation:** linear regression, RMSE 4.8912 hours (R² 0.9313). Gradient boosting is almost tied (RMSE 4.9165, R² 0.9306); then random forest (5.4680) and decision tree (6.2796).
- **Bias versus variance (decision tree, `part_b_tree_depth.csv`):** depths 1 to 3 are **high bias** (both errors are high: depth 1 has train RMSE 11.6334 and validation RMSE 12.1324, a gap of only 0.4990, so the tree is too simple). Depths 8, 12 and unlimited are **high variance**: depth 8 has a gap of 3.5025, depth 12 a gap of 6.0560, and no depth limit has train RMSE 0.0000 against validation RMSE 7.7890 (gap 7.7890, memorising training rows). The best depth is 6 (validation RMSE 6.2796).
- **Learning rate (gradient boosting):** 0.1 is best (validation R² 0.9306). At 0.01 R² is only 0.7127 because with 100 trees each tree adds too little, so the model is still under-fitted (too slow). At 1.0 R² falls to 0.8440 because each tree overcorrects and the ensemble overshoots.
- **Cross-validation disagrees with the validation ranking.** On the 1,020 training-plus-validation rows (shared 5-fold object) linear regression scores mean R² 0.9261 (std 0.0048) and gradient boosting 0.9352 (std 0.0044). I would **ship gradient boosting**: the cross-validated estimate uses 1,020 rows and five splits and is much more stable than a single 180-row validation set, where the two models differ by only 0.0253 hours of RMSE; boosting can also capture interactions (for example sale-window and rain effects that vary by service type and distance) that a linear model cannot. The gap is modest, so linear regression remains a good, simple fallback.
- **Final test score (protocol: lowest validation RMSE, scored once):** linear regression on the 180 test rows gives MAE 3.5671 hours, RMSE 4.5235 hours and R² 0.9493. Gradient boosting was not scored on the test rows, so before shipping it I would confirm it on fresh data.

## Model results (classification)

Files: `part_c_models.csv`, `part_c_feature_scores.csv`, `part_c_selectk.csv`, `part_c_tuning.csv`, `part_c_thresholds.csv`, `part_c_final_test.csv`, `part_c_final_config.csv`. The stratified split is 840 / 180 / 180 with 195 / 42 / 41 delayed parcels.

- **Blind baseline:** predicting "not delayed" for everything has validation accuracy 0.7667 (TN 138, FN 42), but recall 0 and precision 0, so it catches none of the 42 delayed parcels. Because roughly 23% of parcels are delayed, accuracy hides a useless model. Trained models reach accuracy 0.8833 to 0.9056; logistic regression F1 0.8046, best tree (depth 6) 0.7470, default forest 0.7848.
- **Noise columns:** the five bookkeeping columns hold a combined 0.2245 of the forest's importance across 17 columns (random forests split on any continuous column, so importance is spread onto noise). The F-score separates them cleanly: all five have f_rank 8 or lower (ranks 8, 12, 14, 16 and 17), with F-scores of at most 4.5847, while the weakest of the real top 7 (`sale_event_flag`) has 36.7281. All five fall outside the top 7. The top 7 are `distance_km`, `hub_tier`, `hub_daily_capacity`, `n_stops`, `promised_hours`, `rain_flag`, `sale_event_flag`.
- **What the k table shows (`part_c_selectk.csv`):** validation F1 is 0.6988 for k=5, 0.8333 for k=7, 0.7857 for k=10, 0.8049 for k=12 and 0.7848 for k=17. k=7 is best: k=5 drops two genuine signal columns, and larger k lets noise columns back in.
- **Tuning did not beat the untuned forest on validation.** Grid search (135 fits, best CV accuracy 0.8952) reached validation F1 0.7750, randomized search (45 fits, CV accuracy 0.8905) 0.7848, and the untuned forest on the same 7 columns 0.8333. With only 42 delayed parcels in validation, one parcel moves F1 by about 0.01 to 0.02, so these differences are partly noise: a small validation set cannot reliably rank configurations, and tuning against it risks fitting its quirks. I therefore kept the simplest configuration (`default_forest_same_7_features`, n_estimators 100, no depth limit, min_samples_leaf 1).
- **Alert threshold = 0.5.** The rule picks the highest threshold whose validation recall is at least 0.80. At 0.5 validation recall is 0.8333 (35 of 42) with precision 0.7955; at 0.6 precision rises to 0.8889 but recall drops to 0.7619, which violates the rule. Lower thresholds buy recall at the cost of calls: at 0.3 recall is 0.9286 but precision falls to 0.6964, and at 0.1 recall is 0.9762 with precision 0.4824.
- **One test evaluation at 0.5:** precision 0.6889, recall 0.7561, F1 0.7209, accuracy 0.8667 (TN 125, FP 14, FN 10, TP 31). Test recall is lower than validation recall (0.7561 against 0.8333) and below the 0.80 operations target. The difference is about three parcels, and the test set has only 41 delayed parcels (one parcel moves recall by about 0.024), so it is within sampling noise, but it should be read as "recall is probably around 0.75 to 0.83", not as a guaranteed 0.80.

## Operations recommendation

**Escalate segment (9 hubs, mean delay rate 0.4600; `hub_segments.csv`, `hub_profile.csv`):** Nagpur (HUB13, 0.46), Kochi (HUB15, 0.36), Patna (HUB17, 0.46), Ranchi (HUB18, 0.38), Guwahati (HUB19, 0.62), Raipur (HUB20, 0.48), Bhubaneswar (HUB21, 0.40), Siliguri (HUB23, 0.44) and Agartala (HUB24, 0.54). The other segments are Standard (7 hubs, delay rate 0.0257) and Watch (8 hubs, delay rate 0.1550).

**Tier label does not match behaviour for four hubs (`tier_vs_segment_mismatch.csv`):**
- HUB07 Kolkata is Tier 1 but behaves like a Watch hub (delay rate 0.14): do not give it the light Tier 1 playbook.
- HUB13 Nagpur and HUB15 Kochi are Tier 2 but fall in Escalate (0.46 and 0.36): treat them with the Escalate playbook, not the Tier 2 one.
- HUB22 Dehradun is Tier 3 but behaves like a Watch hub (0.20): it does not need full escalation.
The tier label should therefore be treated as an administrative size label; the playbook should follow the observed segment, and tiers should be re-checked regularly.

**Alert rule:** alert when predicted delay probability is at least **0.5**. From `part_c_final_test.csv`, precision is 0.6889, so about 7 of every 10 flagged parcels are really delayed; recall is 0.7561, so about 3 of every 4 delayed parcels (roughly 7 to 8 of every 10) are caught before they are late.

**New parcels (`new_shipment_actions.csv`):** 8 of the 48 new parcels are flagged; 6 of those sit in Escalate hubs and need a hub-manager escalation, and 2 get a proactive customer call.

**Why K = 3 (`part_d_separation.csv`):** across-over-within ratios are 2.8940 (K=2, sizes 15-9), 5.3928 (K=3, 9-8-7), 6.3047 (K=4, 8-7-5-4) and 6.8866 (K=5, 8-7-4-3-2). The ratio mechanically keeps rising as clusters are split, but the big gain is from K=2 to K=3 (+2.4988) and later gains shrink (+0.9119, then +0.5819). K=4 and K=5 each contain clusters of fewer than 6 hubs (5 and 4 hubs; 4, 3 and 2 hubs), too small to carry their own playbook, and operations runs exactly three playbooks, so K=3 is kept.

## Production plan

**(a) Production-readiness characteristics mapped to the repository**

| Characteristic | Where it lives |
|---|---|
| Accuracy | Held-out evidence in `part_b_metrics.csv` (test R² 0.9493) and `part_c_final_test.csv` (precision 0.6889, recall 0.7561) |
| Reliability | `clean_shipments` handles duplicates, bad spellings, sentinel weights and gaps; the scored batch has 0 missing values in the actions file |
| Reproducibility | Pinned `requirements.txt`, fixed `random_state` values, committed generator, fixed run order, byte-identical reruns of `predict_delay.py` |
| Performance (speed) | A single 100-tree forest on 7 selected columns scores a batch in one vectorised call |
| Maintainability | One shared `src/shipment_prep.py`, one script per Part, named output CSVs |
| Consistency | `predict_delay.py` imports the same `clean_shipments` and `build_features` as training, uses `feature_order.csv` and the stored `impute_values.csv` medians |
| Monitorability | Every scored parcel keeps its `delay_probability`, `flagged` and `action`, so flag rates and later outcomes can be compared |

**(b) Quantities to monitor, with numeric triggers**
1. Weekly delayed share of delivered parcels (baseline 0.2317): investigate if it moves more than 0.05 away from the baseline for the same kind of week.
2. Weekly share of parcels flagged (about 0.25 on the test set: 45 flagged of 180): investigate if it leaves 0.15 to 0.35 for two consecutive weeks.
3. Recall on parcels whose outcome is now known (validation 0.8333, test 0.7561): retrain if rolling 4-week recall drops below 0.65.
4. Feature drift, for example median `distance_km` (314.95 km at training time) or mean `n_stops` per hub: investigate if either shifts by more than 10%.

**(c) Retraining and the sale window.** Retrain monthly on the latest delivered parcels and re-run `part_d_segments.py` so hub segments follow current behaviour; retrain immediately if trigger 3 fires. The 15 to 28 September sale window (`sale_event_flag`) must be compared with the same kind of event (the previous sale window), never with ordinary weeks, because delay rates during a sale are expected to be higher and would otherwise cause false alarms. Data drift here would look like: a different hub or service mix, longer lane distances or more stops per route, a hub moving to another segment (as Nagpur and Kochi already differ from their tier), new service types or promise times, or changed weather patterns.

## Limitations

- **Synthetic data:** all relationships come from a generator, so real-world performance, especially the near-linear behaviour that makes linear regression so competitive, may be very different.
- **Small test set:** the test set has only 41 delayed parcels, so precision (0.6889) and recall (0.7561) have wide uncertainty; one parcel moves recall by about 0.024.
- **Threshold and configuration chosen on one validation split of 180 rows** (42 delayed): the three tuning candidates were separated by only a few parcels, so the choice of configuration and threshold 0.5 may not be stable.
- **Hub segments rest on 24 hubs with 50 parcels each** from one 90-day period; K-Means with K=3 is imposed by the business, not discovered, and four hubs already disagree with their tier label.
- **Winner of the regression comparison depends on the split:** linear regression won on validation while cross-validation preferred gradient boosting.
